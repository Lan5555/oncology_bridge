# Redistribution request selection

Update: [API_GAPS_BACKEND_CONTRACT.md](API_GAPS_BACKEND_CONTRACT.md) now defines the dispatch/delivery endpoints, canonical `DELIVERED` completed-list filter and required `allowedActions` response field. Those controls are wired in the frontend; their backend deployment remains unverified.

The new-transfer dialog uses named medicine batches and recipient facilities. Users do not type internal IDs. IDs remain the values sent to the existing transfer endpoint.

- `GET /api/inventory?page=1&limit=100`: return facility-scoped inventory with stable IDs, medicine names, batch numbers, available quantities, units and expiry dates. The dialog supports loading further pages and excludes explicitly unavailable/deleted medicines, nonpositive stock, expired batches and quarantined/disposed stock using the existing inventory presentation filter. The backend remains authoritative for transfer eligibility.
- `GET /api/transfers/suggest?inventoryItemId=<id>`: return recipient suggestions for the selected stock batch. Supported arrays are a direct response array or `recipients`, `suggestions`, `facilities`, `items` or `data`. Each entry needs `{id, name, city?, distanceKm?}`, or `{facility: {id, name, city?}, distanceKm?}`. A direct entry can also supply `facilityId` in place of `id`. Never return unauthorized facilities or the donor itself. Apply the backend's eligibility policy; the frontend does not assume a radius or substitute the general network directory. An empty array means no suggestions, while missing/invalid recipient details display an error.
- `POST /api/transfers`: payload remains `{inventoryItemId, recipientFacilityId, quantity}`. Recheck ownership, caller permissions, recipient eligibility, current available stock, unit consistency, expiry and medicine state atomically. The UI limits whole quantities to displayed stock, but that snapshot may change before submission.

Suggestion failures display a retry action and block submission. Changing the batch clears the recipient selection and fetches new suggestions. Successful creation closes the form and triggers the existing transfer-list refresh. Backend delivery/completion status remains authoritative; approval is not a delivery confirmation.

Deployment acceptance: select named batches from real stock, check pagination, recipient suggestions, changed-batch/stale-response handling, empty and denied responses, stock quantity validation and successful request/approval refresh with actual facility credentials.

The Redistribution Centre offers an optional Graph view; List view and the original request form remain available. The graph starts empty. Its required path is Medicine batch ? Recipient facility ? Transfer quantity ? Review transfer request. Quantity has two required inputs: Recipient (facility output) and Amount (Number or math output). It outputs a typed transfer allocation carrying the batch ID, recipient ID and quantity together. The final request node accepts this allocation plus an optional boolean condition; separate batch/recipient/number connections to the final node are not supported.

The form and graph share inventory pagination and recipient-suggestion loading. Changing a batch clears the recipient. Empty suggestions display a server-empty state with retry and never fall back to an unrestricted facility list. Inspect GET /api/transfers/suggest?inventoryItemId=<id> and the backend eligibility filters to diagnose an empty recipient list; the frontend cannot establish the server's reason from an empty array.

Completing the connections enables Review transfer request. Clicking it opens a final confirmation modal with a snapshot of medicine, batch, expiry, recipient, quantity, unit, available stock and condition result. Opening or cancelling the modal performs no write. Back to graph preserves the draft. Only Confirm and send request calls the existing POST /api/transfers with {inventoryItemId, recipientFacilityId, quantity}. The graph is locked during review; confirmation revalidates the current graph and requires its payload to match the reviewed snapshot. Duplicate confirmation is guarded, errors keep the preview/draft intact, and success closes the modal, clears batch/recipient selections, reloads stock and refreshes the transfer list. The backend must still recheck stock, eligibility, ownership and permissions atomically. Approval, dispatch and receipt remain separate actions.

Wires support dragging in either direction, typed drop targets and rerouting. Invalid drops and Escape preserve existing connections. Only source variables and batch/recipient selectors accept direct value entry; there are no manual quantity overrides or inline operator defaults. Math, comparisons and AND/OR need two wired inputs; NOT and boolean preview need one. Use Number/math outputs for numeric comparisons before the Quantity allocation stage. Missing inputs, division by zero and nonfinite math results stay unknown. Fractional, nonpositive and excessive quantities are blocked. A connected optional condition must be true. Drafts survive view switches but reset on leaving the page; no workflow-storage endpoint has been added.
